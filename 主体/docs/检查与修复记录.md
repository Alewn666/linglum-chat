## 2026-11-01 18:3x · 扫码入群（V0.3.1 / 53）

**需求**：「再加上可以扫码入群。」

**设计（为什么不把群密钥交给服务端）**：
群消息是端到端加密的，服务端没有群密钥，所以二维码不能只是"服务端记账"。
做法：**群密钥用「一次性口令」加密后直接写进二维码本身**，二维码长这样：

```
linglum://gjoin?t=<入场token>&s=<一次性口令>&w=<用口令加密后的群密钥>
```

- 服务端只发入场 `token`（7 天有效，可重复生成，重新生成 = 旧二维码作废），并负责凭 token 把人加进群；
  服务端**永远看不到群密钥**（`w` 是客户端解密的，服务端只是原样存进 `group_keys` 备查）。
- 扫码的一方：拿到 `s` → SHA-256 派生 AES 密钥 → 解开 `w` 得到群密钥 → 本地存在 `gkey_<gid>` → 再调接口入群。
- 安全边界：**谁拿到二维码，谁就能读这个群的历史消息**（因为密钥在码里）。所以给了 7 天有效期，
  重新生成二维码就作废旧码 —— 和微信"群二维码 7 天失效"的模型一致。

**服务端（`主体/server/app.py`）**：
1. 新表 `group_invites(token PK, gid, created, expires)`（自动建，无需迁移老库）。
2. `POST /api/groups/<gid>/qr`：群成员才能生成；`secrets.token_hex(12)`，7 天有效；每个群最多留最近 10 个。
3. `GET /api/groups/join/info?token=`：扫码后先看群名/人数/自己是否已在群里；过期 → 410。
4. `POST /api/groups/join`：凭 token 入群（写 members + `group_keys(..., wrapped_by='qr')`）。
5. 审计：`group_qr` / `group_join_qr`。

**客户端**：
1. `Crypto.keyFromSecret()`：SHA-256 派生 AES 密钥。
2. 聊天信息页新增「🔳 群二维码」行 → `showGroupQr()`：
   生成 32 字节随机口令 → 加密群密钥 → 换 token → 弹出二维码（230dp）+ 文案「7 天内有效」。
3. `handleScan()` 先认 `linglum://gjoin?`：调预览 → 用口令解出群密钥 → `POST /api/groups/join` →
   把密钥存 `gkey_<gid>` → 刷新群列表 → **直接进群会话**。
4. `unwrapGroupKey()`：`wrapped_by == "qr"` 时从本地 `gkey_<gid>` 取密钥（不再走 ECDH）。

**验证**：
1. 服务端临时实例（5193）**8 项断言全过**：建群 → 生成 token → 扫码预览（群名/人数/未加入）→
   扫码入群 200 → 入群后 `/api/groups` 能看到且 `wrapped_by=qr` → 非成员生成二维码 403 →
   无效 token 预览/入群 404。
2. 生产部署：镜像/容器重建；`/api/health` ok；`/api/groups/join/info` 无 token=401（接口在且受保护）。
3. 客户端：javac 通过 → 构建（systemd-run 限内存 550M）→ **53 / V0.3.1**，386078B，
   md5 `714ccec1aab21364bf4e2e2638660989`；dex 校验 `showGroupQr`/`joinGroupByQr`/`keyFromSecret`/`showQrDialog` 都在；
   线上 `/api/version`=53、下载 200 且 md5 一致。
4. **未验证**：真机（无法跑 Android 模拟器）——扫码要两台设备实测。

**已知取舍**：二维码 = 群钥匙，泄露即等于泄露历史消息；7 天后自动失效，重新生成即作废旧码。
以后若要做"扫码但看不到历史"，得给新成员单独发一把新群密钥（相当于换群密钥），成本高，暂不做。

## 2026-11-01 16:4x · 键盘弹出时输入栏被盖住（V0.2.6 / 46）

**现象（用户截图）**：点输入框弹出输入法后，聊天页的输入栏**完全消失**，消息列表直接顶到键盘上沿；
同一时刻微信的输入栏是贴着键盘上方、且能看到最新一条消息。用户要求"学微信"。

**为什么 manifest 里的 `adjustResize` 没起作用**：`AndroidManifest.xml` 一直写着
`android:windowSoftInputMode="adjustResize"`，但 Activity 同时用了
`SYSTEM_UI_FLAG_LAYOUT_STABLE | SYSTEM_UI_FLAG_LAYOUT_FULLSCREEN`（V0.1.4 为了让顶栏背景画到状态栏后面）。
在这台小米（HyperOS）上，这个组合下窗口**不会因键盘而缩小**，键盘直接盖在内容上 → 输入栏被压在键盘下面。
（顶栏那套是三轮才调好的，不能为了键盘去动它，所以键盘这块自己做。）

**修法：自己算键盘高度，给根视图补底部 padding**（`installImeHandling()` + `applyImePad()`，在 `reset()` 里装）：
1. 两个信号取最大值，避免单一 API 在某些 ROM 上不报：
   - `getWindowVisibleDisplayFrame()`：`decorH - visibleBottom` = 被键盘盖住的高度（最经典、跨版本可用）；
   - `OnApplyWindowInsetsListener`：API 30+ 用 `insets.getInsets(Type.ime()).bottom`，以下用 `getSystemWindowInsetBottom()`。
2. 小于 100dp 的当导航条忽略（导航栏也会报在 bottom inset 里）。
3. **防重复垫高**：记住"没键盘时的窗口高度"`rootMaxH`；若系统这次真的缩了窗口（`rootH` 变小），
