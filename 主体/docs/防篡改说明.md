# 防篡改机制（v1.3，2026-10-31）

## 威胁模型
服务器（NAS）虽然看不到明文，但理论上可以：
1. 改消息内容
2. 改「谁发给谁」
3. 改时间戳
4. 删除、重排、重放消息

## 三道防线

### ① 内容加密 + AEAD（AES-256-GCM）
任何对密文的改动都会导致 GCM 认证失败，消息直接解不开。

### ② 数字签名（ECDSA P-256 / SHA-256）
每条消息发送前，发送方用**自己的私钥**对下面这个规范串签名：

```
发件人 \n 收件类型 \n 收件人 \n 时间戳 \n 序号 \n 前一条哈希 \n SHA-256(正文)
```

接收方用发送方公钥验签。所以：
- 改正文 → 正文哈希变 → 签名对不上
- 改收件人/时间 → 签名对不上
- 服务器把发件人改成别人 → 签名对不上（它没有别人的私钥）

### ③ 发件人写进密文
密文信封里带 `f`（发件人）。接收方比对「密文内的 f」与「服务器给的 from」，
不一致直接判篡改——服务器换不了这个字段（它没有密钥）。

### ④ 消息链（seq + prev hash）
每条消息带序号 `s` 和上一条的签名哈希 `p`。接收方要求：
- `s` 必须等于本地记录的序号 + 1
- `p` 必须等于上一条的哈希

删消息、调顺序、重放旧消息 → 链断 → 界面标红「消息链不连续」。
链状态按「会话 + 发送方」分开记录，群聊里每个人各有一条独立链。

## 界面表现
- 校验通过：正常显示
- 校验失败：正文下方追加 `⚠️ 签名校验失败（消息可能被篡改）` 或
  `⚠️ 消息链不连续（可能有消息被删除、重排或重放）`
- 旧版本消息（无签名）：正常显示，视为「未校验」

## 验证

`主体/server/test_tamper.py`（模拟两个客户端打真实服务端，用 Python 独立实现同一套加密协议）：

```
✅ 发送带签名的消息
✅ 密文内发件人 == 服务端发件人
✅ 正常消息签名验证通过
✅ 改密文 → GCM 认证失败（解不开）
✅ 改服务端时间戳 → 签名失败（被检测）
✅ 改服务端发件人 → 与密文内发件人不符（被检测）
✅ 删掉前一条 → 链断开（被检测）
全部通过 ✅（测试数据已清理）
```

运行：`python3 主体/server/test_tamper.py`（需要 cryptography 库；会自己建临时账号并在结束时清除）

## 仍然防不住的（诚实边界）
- **服务器可以「不投递」**（消息石沉大海）——链断能提示，但无法强制它转发
- **服务器可以看到元数据**：谁、什么时候、给谁、密文多长
- **首次加好友仍有中间人理论风险**——App 显示安全码，建议当面核对
