# 灵珑聊天 · 更新方式改造（V0.0.10，2026-11-01）

## 用户诉求

> 不要总是冷更新，能不能出一下热更新的那个样子？

## 先说结论（技术事实）

1. **普通 Android App 不能静默安装自己**：没有系统签名 / root 的话，装 APK 一定要经过系统安装器，
   用户至少要点一次「安装」。所以"像微信那样无感更新"**不是靠装 APK 实现的**。
2. 微信那种是 **Tinker / Sophix 式的 dex 补丁**：只下发几百 KB 的补丁 dex，App 启动时用
   `DexClassLoader` 加载，**完全不重装**。
3. 我们现在的构建是「javac + d8 + apksigner」纯命令行、无 Gradle、无第三方库，
   做真正的热更新要自己搭**插件化宿主**：宿主 Activity 固定，界面/功能代码打进 `patch.dex`，
   启动时从服务端拉取并反射加载。

## 本轮先做的（V0.0.10，半热：不用再传安装包）

| 之前 | 现在 |
|---|---|
| 发现新版 → 弹窗 → 点「立即更新」→ 弹进度条 → 下载完 → 调起安装 | 启动时**自动后台静默下载**，下完只弹一句「新版本已就绪，立即安装 / 稍后」 |
| 装好的包下次还得重下 | 下载结果记在 `prefs.pending_ver/pending_apk`，下次启动**直接提示安装** |
| 强制更新（`minVersionCode`）仍走原来的强制弹窗 | 不变 |

也就是说：**你以后不用再从微信里拿 APK、也不用点一堆按钮**，打开 App 它会自己在后台把新版下好，
你只要点一次「安装」——这是普通 App 能做到的极限（不 root 的前提下）。

## 真正的热更新方案（下一轮，需你点头）

```
宿主 APK（不常变）
 ├─ MainActivity      ← 只做：初始化 + 检查 patch.dex + 反射加载 + 生命周期转发
 ├─ ChatService / Provider / Crypto / Api   ← 基础能力留在宿主
 └─ patch.dex（从服务器热下载，带 md5 + 版本号）
       └─ UiImpl：所有界面与业务逻辑（现在的 MainActivity 主体）
```

- 改功能 → 只编译 `patch.dex`（约 100~200KB）→ 上传 `data/patch/` → App 下次启动自动拉取生效
- 失败回退：patch 加载失败 / md5 不符 / 版本不匹配 → 直接用宿主内置的那份，不会白屏
- 风险：要把现在 3000 行主界面从 Activity 拆成「宿主 + 插件」（`this` → `host` 的机械改造），
  **必须在你手机上验证一次**，第一版我会先做「空插件 + 加载链路 + 回退」验证，再迁界面
